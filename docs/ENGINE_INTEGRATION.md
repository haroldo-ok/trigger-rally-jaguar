# Actual integration of 42Bastian's jag_3d_engine

Requested upstream: <https://github.com/42Bastian/jag_3d_engine>, pinned to `f8bc66bf27346f73ec91719b62932b9ceef37d50`. Copyright © 2026 42Bastian, MIT; complete notice at `licenses/jag_3d_engine-MIT.txt`.

This is the **actual Jaguar GPU renderer**, not a repository reference, host renderer or a demo ROM renamed as Trigger Rally. The original CPU demo scene/game loop is replaced with native Trigger Rally game state, controller scanning, converted source assets and physics. The C runtime submits scene data to the adapted renderer.

## Responsibility split

| Processor | Real implementation |
|---|---|
| Motorola 68000 | Real cartridge/bootstrap host; copies the native DSP image from ROM, starts Jerry and sleeps |
| Jaguar GPU | Video/object-list setup, VBL handler, terrain preparation, object/camera transforms, normal lighting, clipping/culling, triangle buckets and textured/Gouraud blitter rasterization, double-buffer swap |
| Jaguar DSP | Actual C game/controller/50-Hz physics/checkpoints/HUD/scene preparation/RAM replay, plus opposite-bank three-voice PCM IRQ/SSI output |

No JavaScript interpreter, browser/WebGL scene, host physics callback, external video or fabricated success telemetry is involved at runtime or in the actual-ROM E2E.

## Memory and submission ABI

The complete assembled GPU program image is embedded in the native DSP image inside the 68000 cartridge payload and copied to external RAM at **`$2000`**. Its startup copies executable overlays into the GPU's small local RAM. The final engine overlay ends at **`$F03F38`**, below the reserved local stack top at `$F03FFC`; the overall external image ends at `$3C00`. These numbers are from the supplied build log, not a guessed GPU capacity.

The DSP configures scene records and camera/light parameters only after the previous GPU command completes. After publishing a scene, it computes the next physical pose concurrently; terrain-changing menu operations wait first. At telemetry `$1000 + 4`:

- `2`: initialization in progress.
- `0`: GPU has finished/swapped; CPU may prepare another scene.
- `1`: CPU has submitted a complete scene for rendering.

The GPU waits for `1`, invokes the real renderer, waits for the blitter and VBL swap, increments its own completed-frame counter at `$1000 + 12`, then writes `0`. The DSP game maintains the legacy CPU/game-frame counter at `$1000 + 16`; the original 72-byte telemetry prefix remains compatible. Body forward-direction diagnostics are appended at offsets 72/76. The test reads both and the actual framebuffer; a moving emulator VBL alone does not count as game progress.

Scene descriptors keep the original engine's 52-byte fixed object prefix, then nine signed 32-bit Q15 matrix coefficients and a signed 32-bit **Q8 geometry scale**, for a **92-byte `GPUObject`**. Target `static_assert`s and the asset test guard this layout. Normals remain unit normals and do not receive object scale. This replaces an earlier attempt to embed model scale in a clamped matrix, which had squashed larger source models.

Target coordinates map the source world `(x, y, z)` onto engine `(x, z, y)` and preserve the required heading offset. Textures are 64×64 native CRY words; opaque source black is kept distinct from the transparent key. Source alpha-zero texels become `$0000`; blitter data-comparison transparency uses that key. This is alpha testing, **not** general blending or original additive checkpoint rendering.

## Terrain and object budgets

- 384×200 16-bit CRY framebuffers, plus a separate 1-bit 40-row HUD at the top.
- Per-course heightfield: 128×128, 8 m spacing, 1/8 m height quantization.
- Up to 24 native textures fit the reserved RAM; 21 are currently converted/used.
- Up to 32 object descriptors and 3,600 native faces in the shared scratch/bucket system.
- Visible terrain radius 12 cells; at most 24 nearest scenery objects within 95 m, plus car/wheels and the active checkpoint.
- Full converted source mesh topology remains in ROM; the runtime selects generated LODs to fit the native scene budget.

These are substantive platform adaptations, not claims that the full original world/shader pipeline has been reproduced. See `PORT_STATUS.md` for missing skybox use, original forest population, articulation, materials, particles and other fidelity gaps.

## Audio is a separate native module

The upstream engine's optional Hively tracker path is not used as a substitute for the game's sounds. `src/gpu/audio.js` is a real DSP PCM mixer, driven by converted original Ogg inputs and native game state. It runs independently of the slow CPU render/simulation loop. All 14 files are converted, but not every original effect/mixing behavior is wired; nonzero PCM is tested, not perceptual parity.

## Performance and validation

The exact tested cartridge is identified by `releases/ROM.sha256` and `releases/build-info.json`; current SHA-256 is `6609ab99d63586a3e8093244c3b90cb11cc376b581630de513f087ffa775ee78`.

Both NTSC accurate-core BIOS paths receive the full 21-check interaction/reset regression. The actual desktop application additionally verifies keyboard-driven gameplay and native GPU progress, plus PAL/NTSC boot/menu/reset variants. Five real native-fault cartridges prove the black/deadlock detectors fail for the intended reason. See `BLACK_SCREEN_REGRESSION.md` and the current JSON reports.

The earlier about-0.7-FPS software-float result is historical. The driving correction runs the real game on Jerry, uses local binary32 arithmetic/cached static data and render-only Q15 wheel composition, and overlaps it with Tom. Controlled driving results are roughly 13–18 completed FPS in the recorded examples, with a near-real-time clock and a genuine Base-course finish. See `PLAYABILITY.md` and current reports for exact hashes/scenarios; dense contacts can be slower.

The universal-header ROM entry now supplies an actual 68000 copy bootstrap at `$83F000` for BIOS-off boot; the signed GPU/SBL path remains in place for BIOS-on boot. This fixes the previous demonstrated black-screen path rather than merely forcing a successful BIOS setting in the test.

Using the requested engine and controlled drivable racing are verified by separate gates; full original-game feature/fidelity conversion and hardware compatibility remain incomplete/unverified. No 50/60 Hz frontend refresh figure is substituted for actual game FPS.
